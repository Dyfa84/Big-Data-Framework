Q4
WITH monthly AS (
  SELECT product, date_trunc('month', date) AS month, sum(quantity) AS quantity
  FROM orders
  GROUP BY product, month
)
SELECT
  product,
  month,
  quantity,
  round(
    100 * (quantity - lag(quantity) OVER (PARTITION BY product ORDER BY month))
    / lag(quantity) OVER (PARTITION BY product ORDER BY month),
    1
  ) AS variation_pct
FROM monthly
ORDER BY product, month;

Lab dbt ======================================================

Q1. The bronze CSV files are left untouched. What is the benefit when a bug is found in a transformation, six months later?
The raw data is still intact, so I can fix the transformation and rebuild the silver layer from the original data. Nothing is lost, and the raw source stays available for audit.


Q2. The source reads the whole file on every query. Which other format and layout would you choose if the orders were ingested every hour for years?
Parquet files partitioned by date, for example bronze/orders/year=2026/month=10/day=21/hour=14.parquet. Parquet is compressed and columnar, so queries read only the columns they need. Partitioning lets queries read only the relevant time range, and each hourly load adds a new file without rewriting old ones.


Q3. The silver models are views. What happens when a view is queried, and when is it preferable to a table?
A view stores only the SQL query, so it is re-executed on every read. It is preferable when the data is small or the query is cheap, when results must always be fresh, and when you want no extra storage.


Q4. UUID values are stored in 16 bytes. How many bytes does the VARCHAR representation use?
36 bytes (32 hex characters + 4 hyphens), more than twice the 16 bytes of the UUID type.


Q5. Which strategy for a dashboard displaying customer age? For sales per region?
Age: replace invalid birthdates with NULL (or exclude them), since wrong ages skew the result. Sales per region: accept and monitor (warn), since birthdates are irrelevant to sales.

Q6. Which test would detect random state/zip combinations, and which reference data?
A relationships test (or singular test) checking each state/zip pair against a reference table of valid ZIP ranges per state, e.g. a USPS/Census ZIP-to-state mapping loaded as a dbt seed.
=== Lab dbt: Exercise 4 ===

Where should the reference data come from?
An official source (USPS or Census ZIP-to-state mapping), not hand-written.

Should it be stored as a dbt seed?
Yes if small and stable (~60 rows): versioned in Git, loaded by dbt, usable with ref(). For large or frequently updated data, use a managed source table instead.

Should the validation happen in the silver layer?
As a test on silver, not as a filter: silver stays complete and the issue is visible. Rejecting or nulling rows is a separate choice (as with birthdates).

What happens when the reference data changes?
Update the seed CSV, commit, run dbt seed then dbt build; tests re-run on the new rules. Git history keeps the old versions.

spark RDD ================================================================


What decides the number of partitions textFile() picks by default, for a file this size?
The file size split into input blocks, with a minimum of min(defaultParallelism, 2). A small file like this one gets about 2 partitions.

repartition() and coalesce() both change the partition count. Which one shuffles data, and which one doesn't?
repartition() shuffles (it can increase or decrease the count). coalesce() does not shuffle by default: it merges existing partitions, so it can only decrease the count.


=== Lab RDD: Lazy evaluation and lineage ===

Does a second orders_data.count() create a new stage in the Spark UI? Why?
Yes. Nothing is cached, so Spark replays the whole lineage and rereads the file.

At which point would .cache() change that answer?
Calling it on orders_data before the first count(): the second count would then read from memory.

=== Lab RDD: The multiline address ===

Why does spark.read.csv(multiLine=True) not have this problem, while sc.textFile() does?
The CSV parser tracks quoted fields, so a newline inside quotes does not end a record. textFile() splits blindly on every newline.

What must be true of a file format for a line-oriented reader to be safe?
Every record must sit on exactly one line, with no embedded newlines (e.g. JSON Lines).

=== Lab RDD: Manual parsing of orders ===

What happens if one line has an extra comma inside product?
split(",") returns six values, so the unpacking raises a ValueError and the job fails at the first action that reaches that line.

Where does the DataFrame API perform the equivalent check, and when?
In the CSV reader, against the schema, when the data is read. Its parse mode (PERMISSIVE, DROPMALFORMED, FAILFAST) decides what happens to bad rows.

=== Lab RDD: Key-value RDDs ===

What does groupByKey shuffle, and why is it more expensive?
Every raw (key, value) pair, with no combining beforehand. reduceByKey pre-aggregates per partition, so far less data crosses the network.

For which aggregations is groupByKey unavoidable?
Those needing all values of a key at once and not decomposable into a combiner, such as a median or percentile.

=== Lab RDD: Manual deduplication ===

What plays the role of partitionBy() here?
The shuffle of reduceByKey, which hash-partitions by order_id so equal keys meet on the same partition.

Which version states the intent more directly?
The window function: it declares "latest row per order_id", whereas reduceByKey spells out the mechanics.

=== Lab RDD: Joining orders with users ===

What must be true of the partitioning for Spark to skip the shuffle?
Both RDDs must be co-partitioned: same partitioner and same number of partitions, so matching keys already share a partition.

What changes with leftOuterJoin() if a user_id has no matching user?
The order is kept, paired with None instead of a username. join() would drop it.

What is the risk of calling .collect() on a much larger enriched?
It pulls the whole dataset into the driver's memory, which can cause an out-of-memory crash. Use take(), aggregate first, or write to storage.
